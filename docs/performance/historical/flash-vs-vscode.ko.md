# FLASH + Neovide vs VS Code: GUI 탐색 실험

[English](flash-vs-vscode.md) | [한국어](flash-vs-vscode.ko.md)

**GUI까지 포함해도 FLASH의 프로세스 RSS 합계가 훨씬 작았습니다.**
터미널 Neovim만 완성된 GUI 앱과 비교하지 않도록 **FLASH + Neovide**와
**VS Code Desktop**을 비교했습니다. 자원 사용과 자동화 작업의 탐색 실험이며,
실제 키 입력부터 화면 표시까지의 지연을 측정한 것은 아닙니다.

일반 2천 줄 파일의 안정화 후 RSS 합계는 약 **172MiB 대 1,548MiB**였습니다.
프로세스별 RSS를 더하면 공유 페이지가 중복 계산될 수 있으므로 **실제 RAM
절약량·GPU 전체 메모리·최대 메모리**로 해석하면 안 됩니다. 최종 일반 파일의 편집
명령 중앙값은 FLASH가 낮았지만 실행별 범위가 겹쳤고, 창 포커스 명령도 FLASH 쪽이 낮았습니다.
자동화 호출 경로가 다르므로 그 차이를 체감 속도의 배수로 주장하지 않습니다.

## 환경

- 날짜: 2026-09-28; 설정 커밋 `8ba69f0a521a309a3c68a4158a5b7802aafa0644`.
- Mac mini, Apple M4, CPU 10코어, RAM 16 GB, macOS 27.0 (26A428), arm64.
- Neovim 0.12.5 + 현재 FLASH 설정, Neovide 0.16.2.
- VS Code 1.139.1. 실행마다 새 user-data·shared-data·extensions 디렉토리를 사용합니다.
- 앱별 3회씩 순서를 교대해 **총 6회 실행**, 실행마다 두 파일을 다뤄 **12개 시나리오**.
- FLASH의 LSP 활성화를 차단합니다. VS Code는 별도 확장 디렉토리에 로컬 측정 확장
  하나만 넣고 **개발 모드가 아닌 일반 앱 모드**로 실행합니다. 기존 사용자 확장은
  읽지 않으며 기본 제공 확장은 유지합니다. Python LSP 확장은 설치하지 않았습니다.
  기본 Git·인증·JSON/TypeScript 관련 서비스는 활성화될 수 있으며 목록을 기록했습니다.
- FLASH도 매번 새 config/data/state/cache를 쓰며 저장소의 init.lua를 직접 읽습니다.
  Neovide에 실제 nvim 경로를 전달해 기존 터미널 전용 런처를 우회합니다.
  swap·ShaDa는 사용하지 않습니다.
- VS Code 임시 설정에서 업데이트·확장 업데이트·텔레메트리·실험·워크스페이스
  신뢰 질문·hot exit·AI 기능을 끕니다. 사용자 설정 파일을 편집하지 않으며
  작업은 생성한 임시 파일에서만 수행합니다.
- 양쪽에 1200 × 800 창을 요청했습니다. VS Code는 해당 미등록 옵션을 Chromium에
  넘기므로 **실제 창·편집 영역 크기가 같은지는 검증하지 못했습니다.**
  렌더링 성능의 우열을 단정하지 않는 추가 이유입니다.
- OS 파일 캐시와 데스크톱의 다른 백그라운드 작업은 통제하지 않았습니다.

[원시 데이터](flash-vs-vscode-results.json)에 최종 실행 전부, 프로세스별 RSS,
검증 결과와 파일 해시를 보관합니다. 로컬 경로·PID는 제거했습니다.
측정 도구를 수정하는 과정의 예비 실행과 확장 개발 모드 실행은 통계에 섞지
않았습니다. 측정 확장 자체의 비용은 빼지 않았습니다.

## 절차

파일은 `value_N = N`을 N=0–1999 또는 N=0–59999까지 넣고 UTF-8·LF·마지막
개행으로 저장합니다. Git 밖에 둡니다. 같은 바이트라도 VS Code는 마지막 빈 줄을
추가로 세어 2,001/60,001줄, FLASH는 2,000/60,000줄로 표시합니다.

1. 분리된 앱 프로세스를 시작하고 작은 Python 파일을 엽니다. 측정 코드가 문서
   준비를 알릴 때까지 시간을 잽니다. VS Code는 확장 활성화·`showTextDocument`,
   FLASH는 `VimEnter` 이후 예약 콜백·`redraw!`를 사용합니다. **자동화 준비 표시**이며
   첫 프레임 표시·모든 백그라운드 작업 완료·OS 콜드 스타트 시간은 아닙니다.
2. 작은 파일을 열거나 활성화한 뒤 부모 프로세스에 알리고 3초 후 RSS를 읽습니다.
   작은 파일은 시작 과정에서 이미 열었으므로 이 단계의 활성화 시간은 원시 데이터에만
   두고 처음 파일을 여는 시간으로 비교하지 않습니다.
3. 아래로 200줄 이동하고 마지막 커서 위치를 확인합니다. FLASH는 `normal! j`,
   명시적 `CursorMoved`, 화면 갱신과 지연 0 이벤트 루프 양보를 사용합니다.
   VS Code는 확장 API로 `cursorMove` 명령 200회를 순차적으로 기다립니다.
4. 2–51번째 줄을 `# benchmark edit N`으로 교체하고 50개 결과를 확인합니다.
   FLASH는 버퍼 API·`TextChanged`·화면 갱신·이벤트 루프 양보를, VS Code는
   `TextEditor.edit`의 완료를 사용합니다. 실제 타이핑·자동 완성·포매터 실험은 아닙니다.
5. 같은 문서를 두 창에 나란히 표시하고 포커스를 50회 전환합니다. FLASH는 창 API와
   화면 갱신, VS Code는 편집 그룹 포커스 명령을 사용합니다. 두 편집창이 있는지
   확인하고 VS Code에서는 양쪽이 같은 문서를 표시하는지도 확인합니다.
6. 임시 파일을 저장하고 3초 뒤 RSS를 다시 읽습니다. 추가 분할을 닫고 큰 파일에서
   2–6번을 반복합니다. 큰 파일 열기는 별도로 측정합니다. 작은 문서는 계속
   메모리에 있으므로 후반 RSS는 누적 상태입니다. FLASH의 대형 버퍼 제한도 확인합니다.
7. 결과를 수집하고 해당 분리 앱만 종료합니다. 최종 6회 모두 정상 종료했으며
   커서 위치·편집 내용·분할 창 검증을 통과했습니다.

메모리는 `ps`로 실행한 앱의 주 PID와 자식 프로세스를 찾아 더합니다.
FLASH 쪽에는 **Neovide와 Neovim**, VS Code 쪽에는 **Code 본체·renderer·GPU/helper·
확장 호스트** 중 해당 프로세스 트리에 속한 것들이 포함됩니다. 측정 부모 프로세스,
WindowServer, 다른 편집기와 트리 밖 시스템 서비스는 제외합니다.
공유 매핑이 중복 계산될 수 있으므로 실제 물리 메모리 절약량으로 환산하지 않습니다.

측정 확장은 공식 [편집기·명령 API](https://code.visualstudio.com/api/references/vscode-api)를
사용합니다. 데이터·확장 디렉토리 분리는
[VS Code CLI 문서](https://code.visualstudio.com/docs/configure/command-line#_isolating-vs-code-instances)를
참고했습니다.

## 결론과 한계

이 로컬 데스크톱 환경에서는 **GUI 부담까지 포함한 FLASH + Neovide의 프로세스
RSS 합계가 확실히 작았습니다.** 자원 비용에 대한 좁은 결론이며 VS Code가
항상 그만큼의 물리 RAM을 쓴다는 뜻은 아닙니다. GUI 자체의 부담도 있으므로
이전 터미널 FLASH 메모리 값을 GUI 앱 전체 메모리로 재사용하면 안 됩니다.

일반 파일 편집 명령은 FLASH 약 27ms, VS Code 약 32ms가 중앙값이었지만,
VS Code는 약 22–37ms로 FLASH의 약 27ms 범위와 겹쳤습니다. 실행마다 항상
FLASH가 빠른 것은 아닙니다. 일반 파일의 두 앱 커서 명령 시간은 평균적으로
회당 1ms 미만이지만 실제 키 입력을 잰 것은 아닙니다. 모든 최종 표본의 범위를
보존했으며 빠른 결과만 선택하지 않았습니다.

FLASH는 50,000줄 초과 시 무거운 기능을 제한합니다. 6만 줄 결과는 **보호 모드**와
VS Code 기본 대형 파일 처리의 비교이지, 같은 구문 강조·분석 기능을 수행한 비교가
아닙니다. 기능별 원인 분리, 표시 프레임 동기화, 장시간 안정성, 실제 타이핑,
LSP 인덱싱, 디버깅, 추가 확장, 배터리, 사용자 맞춤 VS Code는 측정하지 않았습니다.

**VS Code Remote SSH의 서버 자원 비교가 아닙니다.** Remote SSH에서는 GUI는
로컬 PC에, 원격 서비스는 서버에 실행됩니다. 여기의 데스크톱 RSS를 서버에서
사용하는 메모리라고 제시하면 안 됩니다. 이전 FLASH/pvi/Vim 실험과도 방식이
다르므로 서로 다른 보고서의 절대 시간은 직접 비교하지 않습니다.
