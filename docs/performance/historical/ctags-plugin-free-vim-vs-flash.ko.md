# Ctags 모드: Plugin-free Vim vs ***FLASH***

> 과거 실험 자료입니다. 경로·환경·기능 설명은 기록된 커밋 시점의 조건이며,
> 현재 설치 안내가 아닙니다. 최신 결과는 [성능 문서 목차](../README.md)를 참고하세요.

[English](ctags-plugin-free-vim-vs-flash.md) | [한국어](ctags-plugin-free-vim-vs-flash.ko.md)

이 저장소의 **Plugin-free Vim 설정(`vim/.vimrc`)**과 ***FLASH***를 비교했습니다. ***FLASH***의 LSP를
끄고 양쪽 모두 실제 `gd`에서 Universal Ctags를 사용하도록 측정했습니다.
설정 코드는 바꾸지 않았습니다. Plugin-free Vim·Neovim 전체가 아닌 현재 설정의 비교입니다.

**ctags 모드에서는 모든 항목을 이기는 쪽이 없습니다.** 2,000줄 일반 파일에서는
Vim의 설정 코드 실행·커서 이동·편집 비용이 더 낮았습니다. ***FLASH***는 최초 및
인덱스 준비 후 `gd`, 창 전환, OS가 기록한 최대 RSS가 더 낮았습니다.
대형 파일 제한이 적용된 6만 줄에서는 이동·편집·창 전환도 ***FLASH***가 낮았습니다.

ctags만 쓰고 일반 파일 편집이 중심이라면 **Vim도 합리적인 선택**입니다.
메모리가 부족하거나 정의 탐색·분할 창 이동이 잦다면 이번 측정에서는 ***FLASH*가
유리**합니다. 다만 준비된 인덱스 탐색 차이는 1ms 미만이므로 체감이 극적으로
달라진다고 홍보할 정도는 아닙니다. “***FLASH***는 Vim보다 항상 빠르다”는 결론은
이 결과로 뒷받침되지 않습니다.

## 측정 환경과 공정성

- 날짜: 2026-09-28; 설정 커밋 `a3fdb8728b890eaeb345f0fb7bf57ab813ed2114`.
- Apple M4 Mac mini, 10코어, RAM 16 GB, macOS 27.0 (26A428), arm64.
- Vim **9.2**, 패치 1–1100, Homebrew Huge 터미널 빌드. Vim 9.0 측정은 아닙니다.
- Neovim **0.12.5** Release, 양쪽 모두 Universal Ctags **6.2.1**.
- 같은 120 × 40 PTY, `TERM=xterm-256color`, UTF-8 로케일, 같은 실행 디렉토리.
  양쪽 모두 일반 터미널 UI로 실행하고 출력은 계속 읽어냅니다.
  실제 터미널 앱의 렌더링이나 SSH 통신은 포함하지 않습니다. 터미널 질의에
  응답하지 않는 PTY이므로 시작 시간에 터미널 응답 대기가 섞입니다. 이 수치는
  실제 앱 실행 속도의 우열을 판단하는 근거로 사용하지 않습니다.
- 두 파일 종류마다 각 프로필을 7회 새로 실행: **총 28회**. 실행 순서를 교대합니다.
  swap·ShaDa/viminfo를 끄고 매번 새 data/state/cache 및 태그 인덱스를 사용합니다.
  OS 파일 캐시는 비우지 않습니다.
- 기본 설정과 `retrobox` 테마를 유지합니다. ***FLASH***는 설정 로드 전 LSP 활성화를
  차단하고 포매터는 실행하지 않습니다. 양쪽 모두 플러그인 패키지가 없습니다.
- 같은 소스와 ctags 실행 파일을 쓰되, 실제 `gd` 구현이 각자의 관리 인덱스를
  생성하게 합니다. 미리 만든 tags 파일로 그 경로를 우회하지 않습니다.

앞선 [Package-based Neovim vs ***FLASH*** 실험](flash-package-baseline.ko.md)은 가상 UI와 다른 작업을
사용했습니다. **두 보고서 사이의 절대 수치는 직접 비교하면 안 됩니다.**

## 결과

각 셀은 프로세스 7회 실행의 **중앙값 (최솟값–최댓값)**이며 비용은 낮을수록 좋습니다.
준비된 인덱스의 `gd`는 프로세스마다 20회 탐색한 중앙값을 구하고, 그 중앙값
7개의 중앙값·범위를 표시합니다. 특정 프로세스가 더 많은 가중치를 갖지 않습니다.
최대 RSS는 macOS `wait4`가 반환하는 상주 메모리 최고치를 바이트에서 MiB로
환산한 값입니다. 앞선 실험의 시작 후 RSS와 다르며 전체 프로세스 트리의 메모리

## 입력 파일과 실험 절차

일반 입력은 Python 모듈 100개에 각각 고유 함수 10개, `main.py` 2,000줄이 있는
생성 프로젝트입니다. `module_III.py`에는 `def function_III_JJJ(value=0):`,
스페이스 네 칸의 `return value + J`, 빈 줄로 된 세 줄 블록을 넣습니다.
I는 0–99, J는 0–9이며 식별자는 세 자리로 맞춥니다. `main.py`의 첫 줄은
`function_099_009()`이고 이후 `value_N = N`을 N=1–1999까지 넣습니다.
LF와 마지막 개행을 사용합니다. 새 Git 저장소에 미추적 파일로 두므로 인덱스
생성 시 설정에 구현된 Git 파일 목록 수집도 거칩니다.

대형 파일은 해당 Git 프로젝트 밖에 `value_N = N`을 N=0–59999까지 넣은
60,000줄 파일입니다. 대형 버퍼 제한 대상이며 `gd`는 시도하지 않습니다.
비활성화된 기능을 ctags 속도로 측정하면 의미가 없기 때문입니다.

설정 로드 시간은 얇은 실행 래퍼에서 실제 설정의 `source`/`dofile` 전후를
측정합니다. 이후 런타임 플러그인 로드·파일 열기·터미널 준비를 모두 포함하는
전체 시작 시간은 아닙니다. 첫 탐색 비교 뒤 이 지표를 추가해 전체 28회 측정을
다시 실행했으며, 원시 데이터와 표에는 최종 측정만 포함했습니다.

두 편집기 모두 설정을 불러온 뒤 동일한 Vimscript 측정 코드를 실행합니다.

1. `VimEnter`에서 지연 0 타이머로 `redraw!`를 실행하고 준비 표시 파일을 씁니다.
   부모 프로세스가 실행 시작부터 표시 파일을 발견할 때까지 1ms 간격으로
   측정합니다. 백그라운드 작업 전체나 실제 화면 표시 완료 시간은 아닙니다.
2. 500ms 후 줄 수·테마·대형 버퍼 여부와 ***FLASH***의 LSP 클라이언트 수를 기록합니다.
   일반 파일에서는 `feedkeys('gd', 'xt')`로 실제 매핑을 실행하고 1ms씩 기다려
   이동을 확인합니다. 대상은 `module_099.py`의 `function_099_009` 정의여야 합니다.
   **최초 gd**에는 인덱스 생성·검색·비동기 콜백·대상 파일 열기·화면 갱신이 포함됩니다.
3. 원본으로 돌아와 준비된 인덱스로 20회 반복합니다. 각 `gd`와 대상 화면 갱신만
   재며 원본으로 돌아가는 명령은 제외합니다. 매번 도착 위치를 검증합니다.
4. 원본 버퍼에서 1–600번째 줄로 이동하면서 `CursorMoved`와 화면 갱신을
   명시적으로 실행합니다. 이후 2–101번째 줄을 `# benchmark edit N`으로 교체하며
   `TextChanged`와 화면 갱신을 각각 100회 실행합니다.
5. 같은 버퍼를 세로 분할하고 창 전환·화면 갱신을 200회 반복합니다. 이 세 반복문은
   양쪽 모두 동기 Vimscript로 실행하므로 모든 예약 작업 완료를 포함하지 않습니다.
6. `v:errmsg`를 기록하고 저장 없이 종료한 뒤 OS 자원 사용량을 수집합니다.
   최대 RSS에는 시작·태그 작업(일반 파일)·편집·종료가 포함됩니다. 원시 데이터의
   종료 시 CPU 통계는 편집 반응성이나 전체 프로세스 트리 CPU 사용량으로
   별도 해석하지 않습니다.

[원시 데이터](ctags-plugin-free-vim-vs-flash-results.json)에 버전, 개별 탐색 시간, 종료 코드,
도착 검증 횟수와 전체 결과를 보관합니다.

## 결과를 해석할 때

Ctags는 저장된 소스의 심볼 인덱스입니다. LSP 타입 분석·진단·의미 기반 이름
변경이나 저장 전 소스의 정확성을 제공하지 않습니다. 두 설정의 기능과 구현이
동일하지도 않으므로 ctags 비교가 모든 기능의 동등성을 뜻하지는 않습니다.

초대형 저장소, 느린 네트워크 파일시스템, 중복 정의 선택, 모든 언어, 장시간 사용은
측정하지 않았습니다. 6만 줄 결과는 **기능 제한 상태의 성능**입니다. 모든 기능을
켜둔 처리 속도가 아닙니다. 또한 대형 파일의 최대 메모리에는 태그 생성이 없지만
일반 파일에는 태그 생성이 포함되어 있습니다.

측정 장비는 최신 Mac이며 사용자의 오래된 Red Hat 서버가 아닙니다. 서버의
Plugin-free Vim 버전·터미널·파일시스템·ctags 설치 상태에 따라 결과가 달라집니다.
한 편집기가 언제나 우수하다는 결론 대신 실제 지원 환경과 필요한 기능을 함께
고려해야 합니다.
