# no-pack-speedmode

[English](no-pack-speedmode.md) | [한국어](no-pack-speedmode.ko.md)

**플러그인 패키지 없이, 자원이 부족한 환경을 위한 Native Neovim.**

***FLASH***는 Neovim 내장 API와 설치된 명령줄 도구로 대시보드, 탐색기, 퍼지 검색,
Git 사인, LSP 연동, 자동 완성, 포매팅, 아웃라인, 터미널, 상태줄을 제공합니다.
`no-pack-speedmode`는 이 성능 보고서의 이름입니다. 새 실행 명령이나 토글,
기능을 추가로 제거한 별도의 설정을 뜻하지 않습니다.

비교 대상은 **이 저장소의 현재 pvi와 *FLASH* 설정**입니다. 모든 플러그인 설정과
모든 네이티브 설정을 대표하지 않습니다. LSP 서버·포매터·Git·검색 도구는
별도 실행 파일이므로 모든 기능의 외부 의존성이 사라지는 것은 아닙니다.

## 측정 환경

- 설정 커밋: `a3fdb8728b890eaeb345f0fb7bf57ab813ed2114`.
- 날짜: 2026-09-28.
- 장비: Mac mini, Apple M4, CPU 10코어, RAM 16 GB.
- OS: macOS 27.0 (26A428), arm64.
- 편집기: Neovim 0.12.5 Release, LuaJIT 2.1.1788856981.
- 화면: headless 프로세스에 RPC로 연결한 RGB 120 × 40 가상 UI.
- 파일 종류마다 각 프로필을 7회씩 새로 실행: **총 42회 측정**.
- 반복마다 프로필 실행 순서를 교대하고 같은 파일을 사용했습니다.
- 프로세스마다 새 state/cache 디렉토리를 사용하고 swap·ShaDa를 껐습니다.
  설치된 패키지와 data는 재사용했고 OS 파일 캐시는 비우지 않았습니다.
- `NVIM_APPNAME`은 각각 `nvim`, `nvim-nopack`으로 지정하고 해당 `init.lua`를
  직접 불러왔습니다. 실행 디렉토리는 양쪽 모두 저장소 루트입니다.
- 외부 언어 도구와 편집기 비용을 구분하기 위해 설정 로드 전에 양쪽의 LSP
  활성화를 막았습니다. 포매터도 실행하지 않았습니다.
- 기본 UI 설정은 유지했습니다. Package-based Neovim 테마는 `rose-pine`, ***FLASH***는 `retrobox`입니다.
  스티키·스무스 스크롤·inline blame은 꺼져 있고 아웃라인·탐색기는 열지 않았습니다.

[원시 결과](no-pack-speedmode-results.json)에 개별 측정값, 요약 통계, 파일 해시와
설치된 패키지 커밋을 모두 기록했습니다. 이 결과가 앞선 간단한 5회 비교를
대신하는 공식 문서화 데이터입니다.

## 대형 파일 차이에 대한 추가 확인

42회 모두 `vim.v.errmsg`는 비어 있었고 LSP 클라이언트는 0개였습니다.
6만 줄 파일에서는 두 프로필 모두 공통 버퍼 정책의 제한 상태가 확인되었습니다.
일반 파일 두 종류는 제한되지 않았습니다.

6만 줄의 큰 차이는 별도 탐색 실험 1회에서도 재현되었습니다. 양쪽 모두
이미 `syntax=OFF`, 수동 접기, 커서 행·열 강조 해제 상태였습니다. pvi의
상태 칼럼까지 비운 뒤에도 큰 차이가 남았습니다. 따라서 구문 강조나 상태
칼럼 하나가 원인이라고 단정할 수 없습니다. 정확한 원인은 아직 분리하지
않았으며, 이 극단적인 비율은 README의 대표 홍보 수치로 사용하지 않습니다.
추가 실험의 각 단계는 같은 프로세스에서 순서대로 실행했으므로 워밍업 효과도
있습니다. 원시 데이터에 기록하되 본 실험의 7회 통계에는 섞지 않았습니다.

## 실험 방법과 시간 측정 범위

파일은 생성한 Lua 텍스트 2,000줄, 60,000줄, 그리고 위 커밋의 Git 추적 파일
`nvim-nopack/.config/nvim-nopack/lua/git.lua`입니다. 생성 파일은 Git 밖에 둡니다.
생성 규칙은 `local function sample_N(value)`, 탭 하나의 `if value then`,
탭 두 개의 `return value + N`, 탭 하나의 `end end`로 이루어진 네 줄 블록입니다.
N은 1부터 시작하고 블록을 500회 또는 15,000회 반복합니다. 줄바꿈은 LF이고
마지막 개행도 포함합니다. 실행할 Lua 프로그램이 아닌 합성 편집용 텍스트입니다.

각 프로세스에서 아래 순서로 진행했습니다.

1. **시작:** 프로세스를 생성한 시점부터 UI 연결과 명시적인 첫 `redraw!`가
   완료될 때까지 측정합니다. 모든 예약 작업이 끝났다는 뜻은 아닙니다.
2. 500ms 기다린 뒤 `vim.uv.resident_set_memory()`로 RSS를 읽고, 줄 수·테마·
   LSP 클라이언트 수·공통 버퍼 정책의 제한 여부를 기록합니다.
3. **커서 연속 이동:** 1–600번째 줄의 첫 열로 이동하면서 매번 `CursorMoved`를
   명시적으로 발생시키고 다시 그립니다. 전체 반복은 하나의 Lua RPC에서 실행합니다.
4. **편집:** 0부터 센 줄 번호 1–100을 `-- benchmark edit N`으로 교체하고 매번
   `TextChanged`와 화면 갱신을 실행합니다. 파일은 저장하지 않습니다.
   입력 모드 타이핑이나 자동 완성을 측정하는 실험은 아닙니다.
5. 같은 버퍼를 세로로 한 번 분할합니다. **창 전환:** 두 창 사이를 200회
   이동하면서 매번 다시 그립니다. 이것도 하나의 RPC 안에서 실행합니다.
6. **이벤트 루프를 경유한 이동:** 601–700번째 줄을 별도 RPC 100회로 이동합니다.
   매번 `CursorMoved`와 화면 갱신을 실행합니다. 요청 사이에 예약 콜백이
   실행될 수 있고 RPC 통신 비용도 포함됩니다. 지연 시간이 더 긴 타이머의
   완료까지 보장하는 실험은 아닙니다.
7. 500ms 기다린 뒤 1초 동안의 프로세스 사용자·시스템 CPU 시간 증가량을
   `vim.uv.getrusage()`로 측정하고 RSS를 다시 기록합니다. 저장 없이 종료합니다.

후반 측정에는 앞선 작업이 만든 상태가 남아 있습니다. 서로 완전히 독립된
실험은 아닙니다. Git 차이 계산 같은 비동기 작업은 편집 반복이 끝난 뒤
완료될 수 있습니다. 대기 CPU는 Neovim 프로세스만 측정합니다. 가상 UI이므로
실제 터미널·SSH·Neovide GPU 렌더링 비용은 포함하지 않습니다.

## 서버에서 ***FLASH***를 선택할 이유

코드에서 확인되는 작업량 제한 방식은 다음과 같습니다.

- 인덴트 가이드는 화면 갱신마다 Lua에서 장식을 만드는 대신 내장
  `listchars` / `leadmultispace`로 표현합니다.
- Git 차이 계산은 워커에서 처리하며 실행 중 요청 하나와 교체 가능한 대기
  요청 하나를 유지합니다. 빠른 편집 때문에 작업이 무한히 쌓이지 않습니다.
- 두 프로필 모두 50,000줄 초과, 2 MiB 초과, 한 줄 10,000바이트 초과 시
  공통 대형 버퍼 정책으로 무거운 기능을 제한합니다.
- 스티키·스무스 스크롤·inline blame은 기본으로 꺼져 있습니다.
  네이티브 상태줄 문맥은 커서 이동 시 저장된 심볼 정보를 읽습니다.
- ***FLASH*** 자체는 패키지나 파서를 설치하지 않습니다. 지원하는 외부 도구가
  이미 설치되어 있을 때만 사용하므로 인터넷 없는 환경에 옮기기 쉽습니다.

이는 코드 구조에 대한 관찰입니다. 각각이 몇 ms를 차지했는지 프로파일러로
분해한 결과는 아닙니다. 기능과 테마가 다른 완성된 설정 두 개를 비교했으므로
특정 플러그인 하나가 성능 차이의 원인이라고 단정하지 않습니다.

## 해석의 한계와 추천

**이 결과는 로컬 벤치마크이며 저사양 서버나 SSH에서 측정한 입력 지연이 아닙니다.**
언제나 일정 배수로 빠르다거나 장시간 입력 지연·메모리 누수가 없다는 증거도
아닙니다. 모든 언어를 대표하지도 않습니다. 6만 줄 실험은 기능 제한 상태를
측정한 것이므로 전체 기능이 켜진 대형 파일의 처리 성능으로 홍보하면 안 됩니다.

LSP 분석·인덱싱·자동 완성, 포매터, 탐색기 렌더링, 아웃라인 탐색, 터미널 안의
프로그램, 대규모 저장소 Git 작업은 이번에 측정하지 않았습니다. 무거운 LSP는
어느 설정에서든 가장 큰 부담이 될 수 있고 메모리 수치에도 포함되어 있지 않습니다.
연속 작업 시간에는 뒤늦게 실행되는 모든 작업의 비용이 들어가지는 않습니다.

자원이 부족하거나 인터넷이 없는 서버에서는 ***FLASH* 기본 설정으로 시작하는 것**을
추천합니다. 플러그인의 인터페이스와 편의성이 더 중요하면 pvi를 선택합니다.
서버 성능으로 홍보하기 전에는 해당 Linux 장비에서도 같은 조건으로 측정해야 합니다.
추가 실험에서도 느리거나 차이가 불분명한 항목을 함께 공개하고, 설정·패키지 커밋이
바뀌면 기존 수치를 그대로 재사용하지 않습니다.
