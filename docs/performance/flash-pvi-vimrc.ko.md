# FLASH·pvi·vimrc — 현재 설정 성능 비교

[English](flash-pvi-vimrc.md) | [한국어](flash-pvi-vimrc.ko.md)

현재 세 설정의 공통 편집 작업을 비교했습니다. 일반적인 Vim·Neovim 전체에 대한
결론이 아닙니다. LSP 비용을 제외한 편집기 자체의 기준선입니다.
각 값은 **7회 중앙값(최솟값–최댓값)** 입니다.

FLASH는 세 파일에서 최대 RSS와 창 전환 비용이 가장 낮았습니다. vimrc는 설정
로드가 가장 빠르고 일반 파일의 커서·수정 반복에서는 FLASH보다 비용이 낮았습니다.
pvi도 모든 항목에서 가장 느리지는 않습니다. 보호된 6만 줄 파일의 타이머 기반
커서 이동은 pvi가 조금 짧았으며, 그 값에는 타이머 대기 비용이 포함됩니다.

## 실험 조건과 해석

2026-10-03, 설정 `584ff5a` 기준입니다. Mac mini M4, 10코어, 16 GiB RAM,
macOS 27.0.1에서 Neovim 0.12.5와 Vim 9.2(1–1150 패치)를 사용했습니다.
3개 설정 × 3개 파일 × 7회로 총 **63회** 측정했습니다. 실행 순서를 순환하고
동시에 실행하지 않았습니다. 기존 패키지 폴더를 APFS 복사본으로 보존하고 잠금 파일도 복사합니다. 개별 패키지는
실제 디렉터리이고 그 상위 폴더만 연결합니다. 상태·캐시·세션·undo는
임시 디렉터리로 분리했고, 사용자 파일이나 편집기 설정을 변경하지 않았습니다.

동일한 120×40 PTY와 Vimscript 측정 코드를 사용했습니다. 기본 테마는 유지합니다.
LSP 시작은 두 Neovim 설정 모두 막았고 포매터, 탐색기, outline, AI, 공유 기능은
실행하지 않았습니다. 2천·6만 줄 Python 파일과 실제 Git 관리 중인 FLASH git.lua를
사용합니다. 6만 줄에서는 세 설정 모두 큰 파일 보호가 켜져야 측정에 포함됩니다.

설정 로드 시간은 설정 파일 평가만 측정합니다. PTY 준비 시간은 프로세스 시작부터
VimEnter 뒤 redraw·표식 생성까지로, 터미널 응답이 없는 협상 지연과 부모 측 최대
5 ms 확인 간격을 포함합니다. **사람이 화면을 보는 실제 시작 속도 순위가 아닙니다.**

500 ms 대기 뒤 커서 600회 이동, 줄 100개 수정, 같은 버퍼의 창 200회 전환을
각각 redraw와 함께 측정합니다. 커서·수정 반복에서는 이벤트를 명시적으로 발생시킵니다.
이 반복들은 동기적으로 진행되어 예약된 작업 전체가 시간 안에 끝나지는 않습니다.
별도로 타이머 기반 커서 이동 100회는 이벤트 루프에 양보하며 자연 이벤트 처리를
허용합니다. 그 값에는 타이머 대기·스케줄링도 포함되며 실제 키 입력 지연이 아닙니다.

준비 시 RSS는 준비 표식 직후 측정합니다. 최대 RSS는 macOS wait4의 편집기 단일
프로세스 최대 상주 메모리입니다. 안정화된 메모리, Lua 힙, GUI, LSP·Git 등 자식
프로세스 메모리는 아닙니다. JSON의 총 CPU는 시작·작업·종료를 모두 포함합니다.
모든 정식 실행은 정상 종료, 오류 없음, LSP 클라이언트 0, 수정 내용, 커서 700줄,
편집창 2개를 검증했습니다. 예비 실험 값은 정식 통계에 섞지 않았습니다. 초기 개별 패키지 링크 방식은 설치
복구를 유발해 비교 조건이 맞지 않았습니다. 이 제외 데이터는 별도 JSON에 보존했고,
정식 실험은 실제 폴더 복사본과 잠금 파일로 실행했습니다.

이전 실험은 UI 방식·파일·코드 버전이 달라 수치나 배수를 직접 비교할 수 없습니다.
개별 플러그인의 비용을 분리한 결과도 아니며 과거 병목의 해결을 입증하지 않습니다.
vimrc는 LSP가 없어 기능까지 동등하다는 의미가 아닙니다. 느린 Linux 서버, SSH,
NFS, 실제 LSP와 장시간 사용은 해당 환경에서 별도로 측정해야 합니다.
