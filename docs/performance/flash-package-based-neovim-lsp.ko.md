## 측정 작업과 검증

- 기존 비교와 같은 프로젝트: Python 모듈 100개, 타입이 지정된 함수 1,000개,
  2천 줄 main.py, Git 루트, 120×40 PTY.
- 실행마다 ty 하나만 연결하고 클라이언트·서버 기능 선언, 설정, 명령,
  incremental sync가 동일한지 확인했습니다. 다른 언어 서버는 활성화하지 않았습니다.
- **실제 gd 이동 294회**, 반복 정의 요청 280회, 완성 요청 280회,
  **진단 발생·해제 70사이클**을 ty 재시작 없이 통과했습니다.
  모든 이동은 같은 함수 정의에 도달하고, 완성 응답에는 후보가 있어야 통과합니다.
- 진단 검사는 미정의 이름을 저장해 진단을 기다리고, 정상 코드로 복구·저장해
  진단 해제를 기다립니다. 커서·수정·창 전환 작업도 수정 내용, 최종 커서,
  창 수, 정상 종료와 편집기 오류 없음을 검증했습니다.
- 상태·캐시·세션·undo는 격리했습니다. 설치된 패키지 19개를 잠금 파일과 함께
  복사해 사용했고, 측정 전후 Git revision이 동일했습니다.
  실험을 위해 편집기나 플러그인 코드를 수정하지 않았습니다.

## 해석 범위

직접 정의 요청 속도는 거의 같습니다. 실제 `gd`에는 각 설정의 요청 전달,
UI와 redraw가 포함되며 특정 플러그인 하나의 원인을 분리한 실험은 아닙니다.
자동완성·진단 응답의 측정 범위는 서로 겹칩니다. 동기 커서·수정·창 전환 반복은
지연된 LSP 작업이 측정 구간 밖에서 끝날 수 있고, 타이머 기반 작업은 타이머
스케줄링 시간도 포함합니다. 실제 키 입력부터 화면 표시까지의 지연은 아닙니다.

RSS는 진단 검사 뒤 `ps`로 한 번 측정했습니다. 편집기와 ty의 합계에는 공유
페이지도 합산되므로 고유 물리 메모리나 장기 평균이 아닙니다.
별도 최대 RSS는 편집기 프로세스만의 최고 사용량이며 ty를 제외합니다.

원본의 startup marker는 터미널 질의에 응답하지 않는 절차에서 기록되어 시작
속도 순위로 쓰지 않습니다. SSH·NFS·저성능 Linux·장시간 편집·협업은 측정하지 않았습니다.

2026-10-03의 중앙값은 원본 데이터의 `previous_measurement`에 보존했습니다.
Neovim·ty·Python·설정·패키지 버전이 달라졌으므로 그 차이를 이번 pvi 최적화
10라운드만의 효과로 해석할 수는 없습니다.
