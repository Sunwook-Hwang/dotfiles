두 설정 모두 LSP를 지원하므로 **같은 ty 실행 파일·버전, Python 환경, 프로젝트,
클라이언트 기능 선언, 서버 설정, 변경 전송 지연으로 맞춰 측정**했습니다.

별도 실험이며, 전체 기능이 동일하거나 모든 언어에서 결과가 같다는 뜻은 아닙니다.

## 측정 방법과 검증

2026-10-03, 설정 `aa2cf6b`, Mac mini M4·16 GiB·macOS 27.0.1,
Neovim 0.12.5·ty 0.0.84·Python 3.14.8입니다. 120×40 PTY에서 실행합니다.
프로젝트는 Python 모듈 100개, 타입이 지정된 함수 1,000개, 2천 줄 main.py입니다.
Git 루트를 사용하고 외부 의존성은 없습니다. 실행 순서는 번갈아 바꾸고 병렬 실행하지 않습니다.

벤치마크에서 두 설정의 ty 명령·Python 경로·기능 선언·서버 설정과
`debounce_text_changes=150`을 명시적으로 맞춥니다. 다른 서버는 활성화하지 않습니다.
실제 설정의 LspAttach·진단 핸들러·semantic highlighting·키 매핑은 유지합니다.
서버는 두 설정 모두 incremental sync를 사용했습니다. 모든 실행에서 서버 응답의
기능, 클라이언트 기능 선언, Python 설정과 명령이 동일하고 ty 클라이언트가
정확히 하나 연결된 것을 확인했습니다. 평상시 기본 설정 그대로라는 뜻은 아닙니다.

첫 측정 정의 요청 후 정의 요청 20회와 완성 요청 20회를 직접 같은 LSP API로
측정합니다. 완성 응답은 후보가 있어야 통과하며 팝업 표시 시간은 포함하지 않습니다.
실제 `gd`는 워밍업 후 첫 1회와 반복 20회를 각각 검사합니다. 결과는 모두 같은
함수 정의에 도달해야 통과합니다. 원본 파일로 돌아오는 시간은 제외합니다.
첫 측정 요청 이전에도 서버 초기화·분석이 진행되므로 콜드 인덱싱 시간은 아닙니다.

미정의 심볼을 넣고 저장한 뒤 해당 이름의 진단이 나타나는지, 원래 정상 코드로
복원하고 저장한 뒤 진단이 모두 사라지는지를 5회 반복합니다. 재시작 없이 같은
ty 인스턴스가 유지되어야 합니다. 총 294회 실제 gd 이동, 280회 반복 정의 요청,
280회 완성 요청, 70회 진단 발생·해제 사이클을 통과했습니다.

이후 기존 공통 커서·수정·창 전환 작업도 LSP가 연결된 채로 실행합니다. 동기
반복에서는 예약된 서버 작업이 측정 구간 밖에서 끝날 수 있어 LSP 처리량이나
타이핑 지연으로 해석하지 않습니다. 전체 실행은 정상 종료·오류 없음·수정 내용과
최종 커서·창 수를 검증했습니다.

## 메모리와 해석 범위

진단 사이클 완료 뒤 `ps`로 편집기와 자식 ty의 RSS를 각각 한 번 측정합니다.
합계는 두 RSS의 합이며 공유 메모리까지 합산하므로 고유 물리 메모리가 아닙니다.
이 표본은 최대값·안정 상태 장기 평균이 아닙니다. 편집기 최대 RSS는 별도의
전체 실행 high-water mark로 ty를 포함하지 않습니다.

정의 요청 자체와 실제 gd의 차이는 요청 전달·UI·이벤트 처리 경로가 포함된
관측값입니다. 개별 플러그인의 원인 분석은 하지 않았습니다. 진단은 어느 설정이
항상 빠르다는 결론 대신 이 실험의 범위와 편차로 읽어야 합니다.
SSH·NFS·저성능 Linux·장시간 편집·다른 서버·동시 협업은 측정하지 않았습니다.

설정 코드는 수정하지 않았습니다. 상태·캐시·세션·undo는 임시 공간을 쓰고 패키지는
설치된 버전의 복사본과 잠금 파일로 재사용했습니다. 측정 후 복사본과 설치본의
모든 패키지 Git revision이 동일한 것을 확인했습니다. 임시 프로젝트만 저장합니다.
